# hq008XHSX：125 设备实测（2026-10-26）

设备为 `192.168.0.125:5555`，型号 WS，Android API 29。安装包为 `com.google.android.adxhsx` / `hq008XHSX` / `1.0.4`（versionCode 4），使用当前源码构建的 Debug 包和该渠道既有签名。

## 正式接口链路

通过实际调度及 AdProvider 的 requestFloating 入口验证：

- flow-control 成功，`enabled=true`、`skip_cmp=true`、`popup_log_enabled=false`。
- authorize 成功，首轮 `authorized=true`，隐藏展示、静音、回调超时 180 秒、下一轮间隔 351 秒。
- flow-control、authorize、ad/report 都实际携带非空 `androidid`、`ad_version_name=1.0.4`、`sdk_version=2.8.02`。TCL 未增加 Google 专用的 rdid。
- 真实广告源返回空 VAST，原厂 SDK 返回 -1000，客户端成功上报 AD_ERROR、释放播放器及窗口并结束流程；接着的新请求正常进入 authorize，命中频控拒绝后也正常结束。
- 后台关闭 popup log 时未发送 consent-log-report，ad/report 正常发送并得到成功响应。
- 本轮后台明确跳过 CMP，因此没有把 CMP 弹窗动作作为这次设备验证的覆盖项。

正式广告源当时没有提供可播放素材，不能据此确认线上广告填充率。下面的播放验证使用明确标识的测试 VAST 和仓库已有测试视频，仍经过真实 TCL SDK 的解析、解码、播放与宿主回调。

## 播放与异常回调

Debug 专用 `Hq008DeviceValidationActivity` 提供 lifecycle 与 fixture 两种模式。Release Manifest 已检查，不包含该 Activity。

lifecycle 模式在实际 Android 主线程、Handler 和 TCL SDK 对象上通过以下检查：

1. showAd 后立即取消，已排队的启动不再执行，也不触发播放回调。
2. 暂时注入初始化等待，800ms 总期限内触发一次超时并清空 pending/current 请求，随后恢复 SDK 初始化状态。
3. 保存旧请求的真实 SDK listener，创建新请求后注入旧加载、开始、完成、错误和尺寸错误回调；新请求及其计时器保持不变。
4. TCL 复用底层播放器时，旧控制器回调没有清空新播放器的配置。
5. 上述旧回调之后，新请求的 2500ms 超时依旧触发一次并清理请求。
6. in_flight 跳过、旧 requestId 的超时、旧强制结束及旧日志开关响应，均未结束或修改新 trace。

fixture 模式只替换当前进程 TCL SDK 请求的测试 VAST 响应，使用 `ad-sdk-tcl-demo/src/main/assets/ad-1.mp4`（20 秒测试片），通过 adb reverse 的本地 HTTP 服务提供媒体。实际出现 AD_LOADED、AD_STARTED、AD_PHASE_COMPLETED；完成后 currentRequest 为空、悬浮窗移除。REQUESTED、LOADED、STARTED、COMPLETED 均通过正式 ad/report 得到成功响应。测试请求 ID 使用 `device125-fixture-` 前缀。

另外打开设备上的 YouTube 并观察 8 秒：YouTube 进入前台，未增加广告配置请求、flow-control 请求或旧 delivery 调用；观察期间没有定时轮询，因而不会把调度触发混为前台切换触发。
